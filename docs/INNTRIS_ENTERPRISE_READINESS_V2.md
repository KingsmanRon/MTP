# INNTRIS ENTERPRISE READINESS — v2

Execute this spec. It supersedes v1. The goal is unchanged: make the public site read and behave like an enterprise-ready control product. The execution path has been corrected to avoid two protocol-level mistakes in v1 and to sequence the work against the in-flight mainnet migration.

## Goal

Close the credibility gap between the homepage's public proof claims and what the linked live receipts actually display:

- homepage claims public verification of signature, policy hash, and on-chain anchor
- live PASS receipt currently shows `Policy hash (SHA-256): Not included`
- live PASS receipt currently shows `Receipt integrity: PENDING`
- verdict language is inconsistent across surfaces
- buyer-facing contact address reads like a careers inbox

Fix all of it, in the correct order, without breaking the cryptographic integrity story.

## Locked decisions

1. **Primary buyer-facing contact address**: `sales@inntris.com`
2. **Canonical UI verdict labels**: `PASS`, `BLOCK`, `ESCALATE`
3. **Trust score treatment**: keep, demote to advisory, never primary
4. **Docs tone**: operational and concrete
5. **Public proof model**: the live receipt page must fully support the homepage proof claims
6. **Policy hash going forward**: `policy_hash` is part of the **signed payload** for any receipt generated by a policy-evaluated decision. It is included in the canonical JSON before fingerprinting and signing. Receipts without an evaluated policy display `NOT APPLICABLE`, never `NOT INCLUDED`.
7. **Receipt schema versioning**: bump receipt schema version when `policy_hash` becomes part of the signed payload, so old receipts remain self-consistent and new receipts are distinguishable.

## Non-negotiables

- Do not add new dependencies.
- Do not redesign the site.
- Do not refactor unrelated code.
- Do not change brand colours, layout system, or navigation.
- **Do not retroactively add `policy_hash` to existing signed receipts.** The signature is over canonical JSON with the signature field excluded; adding a field after the fact invalidates the signature and breaks the on-chain anchor story. New receipts only.
- **Do not add `policy_hash` as an unsigned sidecar field on the API response.** A technical buyer will spot it immediately. If the hash isn't inside the signed payload, it isn't proof.
- Use the existing test stack and existing command set in the repo.

### 1.2 Receipt schema change

- Add `policy_hash` as a first-class field in the receipt schema for policy-evaluated decisions.
- `policy_hash` is SHA-256 hex lowercase, computed in the GitHub Action, sent to the backend as a hash only, never raw YAML. (This matches existing architectural rules — do not alter.)
- `policy_hash` is included in the canonical JSON used to compute the receipt fingerprint. Canonical JSON rules unchanged: `sort_keys=True, separators=(',', ':')`, UTF-8, no whitespace, signature field excluded.
- Bump receipt schema version. Old receipts remain valid under their version; new receipts validate under the new version.
- For receipts where no policy was evaluated (e.g. signature-only verification), `policy_hash` is omitted from the payload and the verify page renders `NOT APPLICABLE`.

### 1.3 Generate fresh mainnet receipts under the new schema

- Generate one PASS receipt: agent action, policy evaluated, PASS verdict, `policy_hash` in signed payload, anchored to Base mainnet.
- Generate one BLOCK receipt: agent action, policy evaluated, BLOCK verdict, `policy_hash` in signed payload, anchored to Base mainnet.
- Both receipts use the Inntris Demo org and Demo Agent (`db34c4c8-3a21-43f4-ac0d-7e0fa131d251`).
- Confirm both have valid Ed25519 signatures, valid policy hash verification, valid Base mainnet anchor proofs, and resolved integrity state.

### 1.4 Verify page proof logic

The verify page must resolve every proof check to a final, deterministic, visible state once data is loaded.

- **Signature check**: `VERIFIED` or `FAILED`. No `PENDING` after load.
- **Policy hash check**: `VERIFIED` if hash present in signed payload and validates. `NOT APPLICABLE` if the receipt type does not involve a policy. `FAILED` if hash present but does not validate. Never `NOT INCLUDED`.
- **On-chain anchor check**: For the canonical homepage demo receipts, on-chain anchor must resolve to `VERIFIED` or `FAILED`, never persistent `PENDING`. (These receipts are generated, fully validated, and only swapped in after they are good. Do not generalise this rule to all freshly created receipts in all contexts — transient `PENDING` is legitimate for a brand-new receipt that has not yet been confirmed on chain.)
- **Receipt integrity** (overall): derived from the three above. `VERIFIED` if all pass or are `NOT APPLICABLE`. `FAILED` if any fail. Never `PENDING` after load for the canonical homepage demo receipts.
- `PENDING` is permitted only as a brief loading state before data arrives, or — outside the canonical homepage demo receipts — as a legitimate transient state for receipts still awaiting on-chain confirmation.

The four proof checks are the visual primary on the verify page. Trust score is a small advisory line beneath them.
