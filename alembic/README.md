# Alembic migrations (Phase 1D.1)

Versioned, forward-only schema migrations for the Inntris database.

## Quick reference

```bash
# Install migration tooling (one time, dev/ops machine only).
pip install -e '.[dev]'

# Point at the target database. Alembic reuses the runtime DSN format.
export DATABASE_URL=postgresql://inntris_worker@localhost/inntris

# Apply all outstanding migrations.
alembic upgrade head

# Operator already ran the raw-SQL migrations by hand? Mark the baseline
# as applied without re-running the DDL. Alembic then picks up from here.
alembic stamp 0001_baseline

# Inspect state.
alembic current
alembic history

# Author a new revision. Alembic generates the skeleton under
# alembic/versions/NNNN_<slug>.py; fill in op.execute(...) with the SQL.
alembic revision -m "add foo column to agents"
```

## Why this exists

Before 1D.1 the project used raw `.sql` files under `database/migrations/`
applied with `psql -f`. There was no version table, no way to know what
had been applied, and no way to produce a review artifact of pending DDL
for change management. Alembic fixes all three without forcing us to
re-express the schema as SQLAlchemy ORM models.

## How it works

- `alembic.ini` — config; DSN intentionally blank, resolved from
  `DATABASE_URL` at runtime.
- `alembic/env.py` — env setup. `target_metadata = None` because we run
  raw DDL, not autogenerated ORM migrations. Translates `postgresql://`
  (asyncpg form) to `postgresql+psycopg2://` transparently so the same
  DSN works for both API runtime and migrations.
- `alembic/versions/0001_baseline.py` — re-plays `database/schemas.sql`
  and `database/migrations/002-005*.sql`. Safe to re-run (every DDL
  statement is idempotent) or to `stamp` without re-running.

## Authoring new migrations

1. `alembic revision -m "what you're doing"`
2. Fill in `upgrade()` with `op.execute(sa.text("..."))` blocks.
3. Leave `downgrade()` as `NotImplementedError` unless rollback is
   actually safe — for most of our tables (especially `audit_logs`,
   `merkle_proofs`) downgrade would destroy forensic data.
4. Test with `alembic upgrade head` against a scratch database before
   merging.

Continue writing raw SQL — we do not maintain SQLAlchemy models.

## CI / production gate

Production deploys run `alembic upgrade head` as part of the deploy job
(operator runbook, not automated here yet — wire in Phase 2A).
